# Instructions for AI agents building this repo

Read this together with `PRD.md` (what to build), `design.md` (architecture
and schema decisions already made), and `WORKFLOW.md` (git flow,
milestones, and issues). Don't re-derive architecture that's already
decided in `design.md`; if a decision there looks wrong, say so explicitly
rather than silently diverging.

**Before making any change, and again before committing or pushing, read
`WORKFLOW.md`.** It defines branch naming, commit message format, how to
group commits by issue, and the PR description block to produce once an
issue's work is ready to push. Every commit in this repo references the
GitHub issue it belongs to.

## Ground rules

1. **Don't invent new architecture for a solved problem.** `design.md`
   decides the Airtable schema, the folder structure, the dedup mechanism,
   and where prompts live. If a requirement isn't covered by `design.md` or
   `PRD.md`, flag the gap instead of quietly deciding on your own
   convention.
2. **The source list is data, not code.** Sources are defined only in
   `sources/sources.yaml`, each with a slug, category, type, schedule, and
   a written rationale (PRD §6's pre-build gate). Never hardcode a source
   URL or schedule inside a workflow node (see `design.md` §3, §6).
3. **Prompts live in `prompts/`, not in nodes.** The classify, triage, and
   draft-plan workflows load their prompt from a file (see `design.md` §5).
   Never write prompt text inline in a node, and never maintain a second
   copy of a prompt's logic.
4. **The Airtable schema is defined in `airtable/base-schema.md`.** Any
   table, field, or view a workflow needs must be documented there and
   created there first (see `design.md` §2, §6). Don't add ad-hoc fields in
   the Airtable UI and treat them as ground truth.
5. **Don't bypass the dedup boundary.** `signals.Content hash` is the
   single dedup mechanism and its uniqueness is enforced by Airtable (see
   `design.md` §7). Scout workflows compute the same normalization and
   treat a rejected insert as "already seen," never as an error. There is
   no second dedup store.
6. **Card status is a state machine.** `queued -> approved | rejected` is
   the only allowed transition, and only the review-trigger workflow makes
   it. Only the draft-plan workflow writes `Implementation plan`, and only
   when `Status = approved` and the plan field is empty (see `design.md`
   §3, §7). Never overwrite an existing plan.
7. **Credentials, not keys.** All API keys go into n8n credentials or
   `infra/.env` (see `design.md` §4, §5). Never paste a key into
   `sources.yaml`, a workflow JSON, a prompt, or a commit.
8. **V1 stays single-user, manual-approve.** Don't build notifications
   (PRD §7), a custom dashboard (PRD §6 note), or any auto-execution of
   opportunities (PRD §3). Approval only ever triggers a drafted plan,
   never an action.

## Conventions

- **Language**: no application framework in V1. YAML for
  `sources/sources.yaml`, Markdown for prompts and the schema doc, JSON
  exclusively for exported n8n workflows. Don't introduce a code stack that
  `design.md` didn't specify.
- **Naming**: Airtable table and field names are `snake_case`; source slugs
  and file names are `kebab-case`; workflow names match their bot role
  (scout, classify, triage, draft-plan, review-trigger).
- **File placement**: match `design.md` §6. Workflow JSON lives only in
  `n8n/workflows/` and is generated by `scripts/export-workflows.sh`; it is
  not hand-edited.
- **Workflow changes**: edit the workflow in n8n, re-export the JSON, and
  commit the export. A committed JSON is the source of truth; re-importing
  it after a clone requires re-selecting credentials by hand (documented in
  the export script, `design.md` §5).
- **Schema changes**: edit `airtable/base-schema.md` first, then apply it
  to the base. Never change the schema only in the Airtable UI.
- **Error handling**: a scout or pipeline workflow that fails must fail
  loudly (execution marked failed, error workflow alerted, `design.md` §9).
  Don't swallow a failure into a zero-row success.
- **Comments**: in `sources.yaml`, every source carries a one-line rationale
  (that is the gate); in prompts, comments explain why a step exists, not
  what it says.
- **Secrets**: before committing, check that no real key or credential
  value appears in any staged file.

## Definition of done for a feature

- [ ] Any new source is an entry in `sources/sources.yaml` with slug,
      category, type, URL, schedule, key ref (if any), and a written
      rationale (`design.md` §6, PRD §6).
- [ ] Any Airtable table or field the feature reads or writes is documented
      in `airtable/base-schema.md` before the workflow exists (`design.md`
      §2).
- [ ] Workflow changes are committed as exports in `n8n/workflows/`, not
      hand-written JSON (`design.md` §6).
- [ ] Any new insert path respects the `signals.Content hash` uniqueness
      rule (`design.md` §7).
- [ ] Any approval or plan logic is idempotent: a second run on an
      already-handled card no-ops (`design.md` §7).
- [ ] LLM workflows load prompts from `prompts/`; no inline prompt text in
      a node (`design.md` §5).
- [ ] No credential value or API key appears in any committed file
      (`design.md` §4).

## What NOT to do

- Don't add a second dedup mechanism (an in-memory cache, a second table, a
  "check then insert") because it looks faster; `signals.Content hash`
  uniqueness is the single mechanism (`design.md` §7).
- Don't build notifications, a live dashboard, or auto-execution of
  opportunities in V1 (PRD §3, §7).
- Don't hardcode an Airtable base id or a source URL in a workflow "just
  for now"; that bakes environment state into committed exports
  (`design.md` §5, §8).
- Don't create Airtable fields directly in the UI when the schema doc is
  the source of truth (`design.md` §2, §6).
